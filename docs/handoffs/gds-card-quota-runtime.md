# Card quota runtime integration — in progress

Builds on the deployed provenance schema from PR44. The existing `ServiceEntitlementService` now resolves the latest effective membership revision and canonical qualification in its own snapshot, returns virtual card quota candidates without read-side writes, and provisions a needed grant only inside Serializable consumption. Source IDs are deterministic for policy/tier/definition/window; existing immutable attribution is reused. Revoked candidates are not resurrected. Old active card grants are excluded unless the current policy and qualification still select their context.

Card usage queries pool by user and stable definition across revisions/tiers, by usage creation timestamp in the current service window or all history for lifetime quota. Independent purchased/receipt behavior is preserved. Consumption order follows the policy's card-first/purchased-first setting and appends usage to exactly one source. Reads use RepeatableRead; consumption retains the existing user lock, HMAC operation key, replay check and Serializable retries.

Request-unit metered definitions bind to the five existing server AI operation identities. Unbound codes, boolean definitions and incompatible units do not become executable card grants. Chat, summary, quiz generation, flashcards and learning-path generation now call the request-consumption boundary after their source/ownership checks and before provider attempts. The existing daily abuse guard remains separate. Each actual server request creates a fresh operation key; browser-supplied replay keys cannot obtain repeated provider calls for one debit. When no enabled card-limit policy exists, this boundary performs no debit, preserves purchased quota and does not require the commerce HMAC secret. Under an enabled policy, quota denial stops provider invocation. Units count admitted request attempts; provider errors do not automatically refund usage, matching the existing request-attempt guard semantics.

This registry supplies operation identities only; no thresholds, quotas, provider calls or active policies are seeded. Definition/operation Admin readiness, consumed-quota preview and native controls are still pending, so `CARD_SERVICE_LIMIT_RUNTIME_NOT_IMPLEMENTED` remains unchanged.

Regression evidence: before integration, new tests showed card-first selected purchased quota and a stale active card grant remained consumable. Both now pass. All 179 tests in 19 membership/card/platform suites and Nest build passed locally, including retained receipt pooling. Read-only candidates, custom tiers, bounded-source failure, unsupported bindings, deterministic period IDs, revoked contexts and idempotent provisioning are covered. The PostgreSQL replay fixture now calls the real Prisma-backed service for read-only resolution, persisted provenance, idempotent replay, cross-policy consumption, concurrent last-unit consumption and purchased-first/disabled-policy preservation; remote results are pending and must not be claimed from unit tests.
