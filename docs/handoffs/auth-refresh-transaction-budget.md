# Refresh proof and rotation transaction budget

The authenticated production read-only probe observed an expired access request returning401 followed by refresh500. This is not yet attributed to a specific server stack trace. Source inspection found bcrypt scanning all active remembered-device hashes inside the refresh transaction. A local24-comparison bcrypt12 synthetic benchmark took5502ms; the configured Prisma client uses its normal transaction options. [Prisma's transaction reference](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions) documents the default five-second interactive lifetime. The deterministic regression failed with transaction expiry before this change.

Refresh now verifies the signed token and candidate hash outside the rotation transaction. The transaction reloads the account, rejects missing/blocked/soft-deleted users, and conditionally consumes only the proven token ID/user/hash while still unrevoked/unexpired. Successor issuance remains inside the transaction so a failure rolls back consumption. A competing consumption still returns401. Device lifetime, rate limits, JWT/hash format, response fields and MFA claims are unchanged. This does not increase a timeout or invalidate purchased access, balances or history.

Local focused tests cover the slow proof, account deletion before proof, account state changing before rotation, exact consume predicate and competing consumption. The disposable real PostgreSQL replay additionally injects a six-second proof using the real AuthService and default transaction budget, denies predecessor replay and forces successor issuance failure to prove rollback. It retains purchased grants. Its marker is `GDS_AUTH_REFRESH_SLOW_PROOF_POSTGRES=PASS`; a result is only claimed after the actual CI run succeeds.

A fresh-context adversarial review found no new implementation defect in this narrow correction and requested the issuance-failure rollback check, now included. It also found inherited, unresolved full-contract issues: legacy raw-bcrypt token-prefix ambiguity, logout session-family semantics, shared serialization with password/MFA revoke-all and stale MFA revision handling. These require separate source and database concurrency work before claiming the entire original session requirement complete. This slice neither fixes nor relies on claiming those issues solved. Production refresh500 recovery must be tested against the same retained synthetic session after release; a fresh login alone would not establish recovery.
