# Historical membership reconciliation

Scope: first migration prerequisite for the original GDS card transition. This is a read-only report, not completed entitlement migration, automatic repair or card-benefit fulfillment.

`GET /api/v1/admin/membership/legacy-orders/:orderId/reconciliation` requires an authenticated `platform_admin` and a UUID v4. A missing order returns 404. A supported order returns `orderId`, optional `orderLineId`, `scope=single_order`, `readOnly=true`, `purchasedAccessPreserved=true`, `status` (`reconciled`, `attention`, `blocked`) and findings with machine codes/optional resource IDs. `purchasedAccessPreserved` means the report does not mutate rights; `reconciled` proves only this snapshot comparison, not global migration readiness or permission to repair. Existing response envelope/error handling is unchanged. Provider identities, references, email, amounts and usage contents are not returned.

The report uses one RepeatableRead snapshot, bounded relations (250 course/service/grace components, 1000 effects/grants/usage rows) and a 15-second transaction timeout. Exceeding a bound blocks the report rather than silently truncating. It requires a single fulfilled membership line with matching buyer/version/quantity/currency/amount snapshots. Canonical PayOS/VNPay evidence must match its settlement, payment attempt and paid event. Native wallet capture must match the canonical settlement, captured hold, owner and balanced immutable capture journal. Bank-statement collections, free/no-payment purchases, any refund history and unresolved fulfillment currently remain explicit review exceptions; a subscription or uploaded screenshot is never sufficient payment proof.

Original purchased windows, course/grace sources, service values, subscription and fulfillment-effect identities are compared. Missing, foreign, changed, revoked or unexpected grants produce findings. Service usage is checked for owner, positive quantity, original reset window and non-pooled cumulative quota. Shared receipt quota pools remain manual-review exceptions; they are never reset. Expired purchases may reconcile with their original dates and receive no extension. Card classification/policy state is not used to redefine purchased rights.

No schema, grants, policy activation, provider call, wallet write, grant update, quota reset or production repair is included. The existing checkout replay fixture now calls the actual report on its synthetic fulfilled membership order and compares course grants before/after in disposable PostgreSQL; it runs in both existing test and production-classified modes. It does not call production or a real payment provider.
